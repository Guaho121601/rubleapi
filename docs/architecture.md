# RubleAPI.ru — MVP Architecture

## 1. Выбранный стек

Для MVP выбираем простой монолитный стек без микросервисов:

- **Backend:** Node.js + Fastify.
- **Язык:** TypeScript.
- **База данных:** SQLite.
- **Планировщик загрузки курсов:** cron-задача внутри backend-приложения.
- **Кеш:** in-memory кеш внутри процесса backend.
- **Frontend сайта:** простые серверные шаблоны или статические страницы без SPA.
- **Embeddable widget:** отдельный `widget.js` на vanilla JavaScript без React/Vue.

Почему такой выбор:

- один язык для backend и widget;
- низкая стоимость запуска и поддержки;
- SQLite достаточно для MVP и одного разработчика;
- Fastify даёт простой API-слой без лишней архитектуры;
- нет Docker и нет отдельной сложной инфраструктуры.

## 2. Структура папок проекта

Пример целевой структуры проекта для MVP:

```text
/
  docs/
    product-brief.md
    agent-rules.md
    architecture.md
    agents/
      architect.md

  src/
    app/
      server.ts
      routes.ts
      config.ts

    modules/
      rates/
        rates.service.ts
        rates.repository.ts
        rates.scheduler.ts
        rates.types.ts

      sources/
        cbr/
          cbr.client.ts
          cbr.parser.ts
          cbr.mapper.ts

      widgets/
        widget.service.ts
        widget.repository.ts
        widget-render.service.ts
        widget.types.ts

      api/
        public-api.controller.ts
        widget-api.controller.ts

    db/
      migrations/
      rubleapi.sqlite

    public/
      widget.js
      widget.css

    views/
      landing/

  scripts/
    manual-sync-rates.ts

  package.json
  tsconfig.json
```

Принцип структуры:

- `app/` — запуск приложения и общая конфигурация;
- `modules/rates/` — всё, что связано с курсами валют;
- `modules/sources/cbr/` — интеграция только с ЦБ РФ;
- `modules/widgets/` — логика виджетов и их настроек;
- `public/` — публично доступные статические файлы, включая `widget.js`;
- `views/` — простые страницы сайта и документации;
- `scripts/` — ручные служебные команды для разработчика.

## 3. Основные backend-модули

### 3.1. App module

Отвечает за:

- запуск HTTP-сервера;
- подключение роутов;
- загрузку конфигурации;
- инициализацию кеша и планировщика.

### 3.2. Rates module

Главный модуль MVP. Отвечает за:

- загрузку курсов ЦБ РФ;
- нормализацию данных;
- сохранение курсов в SQLite;
- чтение последних курсов из базы;
- отдачу данных в API и widget.

Минимальные сущности:

- `currency_rates` — курс валюты на дату;
- `rate_snapshots` — информация о конкретной загрузке;
- `supported_currencies` — список валют, которые разрешены в MVP.

### 3.3. CBR source module

Изолирует интеграцию с ЦБ РФ:

- получает исходные данные ЦБ РФ;
- парсит формат ответа;
- преобразует данные в единый внутренний формат.

Это нужно, чтобы backend не смешивал бизнес-логику с логикой внешнего источника.

### 3.4. Widgets module

Отвечает за:

- настройки публичного виджета;
- режимы `free` и `paid`;
- параметры отображения: валюты, цвета, округление, источник курса;
- формирование данных для `widget.js`.

Для MVP платный доступ можно хранить в виде простого `widget_key` или `site_token`, который создаётся вручную без личного кабинета и без автоматической оплаты.

### 3.5. Public API module

Отвечает за публичные JSON endpoints:

- API курсов;
- API для данных виджета;
- отдачу статического `widget.js`.

## 4. Основные API endpoints

Минимальный набор endpoints для MVP:

- `GET /api/rates/latest`
  Возвращает последние доступные курсы ЦБ РФ в JSON.

- `GET /api/rates/latest?base=RUB&symbols=USD,EUR,CNY`
  Возвращает отфильтрованный набор валют для сайта или разработчика.

- `GET /api/rates/date/:date`
  Возвращает курсы на конкретную дату, если они уже есть в локальной базе.

- `GET /api/widget/:widgetKey`
  Возвращает настройки и данные для конкретного виджета.

- `GET /widget.js`
  Отдаёт embeddable-скрипт для вставки на сайт клиента.

- `GET /health`
  Простой технический endpoint для проверки, что сервер запущен.

Примечание по MVP:

- публичное API отдаёт данные только из локальной базы или кеша;
- запросы пользователей не должны напрямую ходить в ЦБ РФ;
- сложная аналитика, кабинеты и админские endpoints не нужны.

## 5. Как работает загрузка курсов ЦБ РФ

Поток загрузки курсов в MVP:

1. Планировщик backend по расписанию запускает синхронизацию несколько раз в день, а после успешного обновления сохраняет snapshot и обновляет кеш.
2. Модуль `cbr.client` делает запрос к источнику ЦБ РФ.
3. Модуль `cbr.parser` разбирает ответ и приводит данные к единому формату.
4. Модуль `rates.service` валидирует список валют и подготавливает snapshot.
5. Данные сохраняются в SQLite.
6. После успешного сохранения обновляется in-memory кеш последних курсов.
7. Все API-запросы и виджеты читают уже локальные данные из кеша или базы.

Поведение при сбоях:

- если ЦБ РФ временно недоступен, backend продолжает отдавать последний успешно сохранённый snapshot;
- ошибки загрузки логируются;
- повторная загрузка может быть запущена вручную через служебный script.

Это соответствует главному правилу MVP: не запрашивать ЦБ РФ на каждый пользовательский запрос.

## 6. Как работает `widget.js`

`widget.js` — это публичный скрипт, который владелец сайта вставляет одним тегом:

```html
<script
  src="https://rubleapi.ru/widget.js"
  data-widget-key="demo"
  data-base="RUB"
  data-symbols="USD,EUR,CNY"
  data-theme="light"
  data-round="2"
></script>
```

Принцип работы:

1. Скрипт загружается с RubleAPI.ru.
2. Считывает `data-*` атрибуты у текущего `script` тега.
3. Формирует запрос к backend за данными и настройками виджета.
4. Создаёт контейнер рядом со `script`.
5. Рендерит HTML виджета внутри изолированного root.
6. Применяет собственные стили, не зависящие от CSS сайта клиента.
7. Показывает брендинг в бесплатном режиме и скрывает его в платном режиме.

Чтобы не ломать стили клиентского сайта:

- основной вариант изоляции — `Shadow DOM`;
- если изоляция недоступна, используются уникальные префиксы CSS-классов;
- виджет не зависит от библиотек сайта клиента.

Требования MVP для `widget.js`:

- один `script`-тег;
- работает на обычном HTML-сайте;
- работает на Tilda и WordPress без отдельного плагина;
- не требует сборки на стороне клиента.

## 7. Что не входит в MVP

В `architecture.md` явно фиксируем границы, чтобы не раздувать первую версию:

- личный кабинет;
- регистрация и авторизация пользователей;
- онлайн-оплата;
- Docker и контейнерная инфраструктура;
- микросервисы;
- банковские курсы;
- криптовалюты;
- live forex;
- мобильное приложение;
- маркетплейс обменников;
- сложная админка;
- frontend SPA;
- WordPress-плагин, интеграции с Tilda, Bitrix, WooCommerce, OpenCart как отдельные продукты.

## 8. Какие этапы разработки идут первыми

Порядок реализации MVP:

1. **Скелет проекта**
   Создать базовую структуру монолита, конфигурацию и запуск HTTP-сервера.

2. **Модуль загрузки курсов ЦБ РФ**
   Реализовать клиент источника, парсинг, сохранение в SQLite и ручную синхронизацию.

3. **Публичный JSON API**
   Поднять endpoints для получения последних курсов и курсов по дате.

4. **Базовый `widget.js`**
   Сделать вставку одним `script`-тегом, загрузку данных и безопасный рендер на внешнем сайте.

5. **Настройки виджета**
   Добавить параметры валют, цветов, округления, брендинга и простой `widget_key`.

6. **Лендинг и документация по встраиванию**
   Описать, как подключать виджет и как использовать API.

7. **Стабилизация MVP**
   Проверить кеш, обработку ошибок, работу при недоступности ЦБ РФ и базовую производительность.

## Итоговое архитектурное решение

Для MVP RubleAPI.ru достаточно одного монолитного backend-приложения на Node.js/Fastify, SQLite для локального хранения курсов, планировщика загрузки данных ЦБ РФ и простого `widget.js` на vanilla JavaScript. Такая архитектура закрывает ключевую ценность продукта и не выходит за рамки первой версии.
